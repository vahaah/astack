# PR review hardening

This repo's settings for the loop live in `.claude/pr-review-hardening.profile.md`. Change the loop's behaviour there, not here.

astack apply writes this file. Fix it in the astack repo. Then apply it again. A skill wins over a command file with the same name, so `/pr-review-hardening` runs this skill, and the repo keeps no command file for it.

## Run the loop

If the Skill tool lists `astack:pr-review-hardening`, invoke it with the arguments `$ARGUMENTS` and follow it. Stop reading this file.

Otherwise run the fallback below. It is the same loop in short form.

## Fallback

With `--pr <n>` in `$ARGUMENTS`, select the head of that PR first, because the profile of the PR head applies:

1. Read `gh pr view <n> --json headRefName,headRefOid,baseRefName,state,isCrossRepository`, and print the three ref values. Stop with principled incompletion when `state` is not `OPEN`. The local branch of the PR is `headRefName`, or `pr-<n>` when `isCrossRepository` is true. A branch of a fork can have the name of a local branch, such as `main`. So the run never takes a checkout by the head branch name of a PR from a fork.
2. When `git branch --show-current` prints the local branch of the PR, stay in this checkout. Otherwise continue in the worktree that holds the local branch of the PR in `git worktree list --porcelain`. When no worktree holds it, run `git worktree add --detach <dir>` with a new directory outside this checkout. Then run `gh pr checkout <n> --branch <local branch>` in it. Continue the run in that worktree. Never switch the branch of this checkout.

CI tests the head of the PR. So every run with a PR does the head check, with `--pr` or without it, before it reads the profile:

1. Without `--pr`, read `gh pr view --json number,headRefOid` for the current branch. The run has no PR only when gh exits 1 and its standard error matches `grep -qi 'no pull requests found for branch'`. Then it skips this check. gh can start that message with an uppercase or a lowercase letter. Each other failure of a `gh pr view` of the run stops the run with principled incompletion, and the run prints the error of gh.
2. Run `git fetch origin <headRefOid>`. When it fails, stop with principled incompletion.
3. Print `HEAD` as the output of `git rev-parse HEAD`, and `PR_HEAD` as `headRefOid`. When `git merge-base --is-ancestor <headRefOid> HEAD` fails, stop with principled incompletion before the baseline.
4. Print `git log --oneline <headRefOid>..HEAD` as `UNPUSHED`. CI did not test these commits, so the final report names each one.

Print `WORKTREE` as the output of `git rev-parse --show-toplevel`. Start every command of the run with `cd <WORKTREE> &&`, because a tool call can start in another directory.

Read the YAML block in the profile. If the file is missing or the block does not parse, stop with principled incompletion. Never run a gate command that you guessed. The fallback has no defaults, so the profile defines every key that it reads. If a key that this section names is missing, stop with principled incompletion. A `null` block, such as `metrics: null`, holds no key, so no key under it is missing. Name the missing key. Print the base branch, each `gates[].command` and the `test.command`, the reviewers and the iteration bounds. When `metrics` is not `null`, also print `metrics.command`. They stay fixed for the run.

The profile's gates mirror the blocking jobs of the repo's CI. A gate that applies but cannot start is an unclean stop. The run never skips it. Each gate in `gates` and `test` defines `gates[].env`, `gates[].requires`, `gates[].setup`, `gates[].when_changed`, `gates[].ci_env`, `gates[].after`, `gates[].tools` and `gates[].rewrites`, or `test.env`, `test.requires`, `test.setup`, `test.when_changed`, `test.ci_env`, `test.after`, `test.tools` and `test.rewrites` for the test gate. A path in `rewrites` is a tracked file that a tool of the gate writes, such as the `next-env.d.ts` of a Next.js app. An empty `when_changed` means that the gate applies to every diff. Otherwise the gate applies when a path in `git diff --name-only --no-renames <BASE_SHA>...HEAD` matches one of its globs and no glob that starts with `!`. A fix can make a gate apply in a later iteration, so decide again before each gate run. `<NAME>` is the `gates[].name` or the `test.name` of the gate in upper case, with `-` replaced by `_`.

A glob matches the whole repo-relative path. `*` matches inside one folder, and `**` matches across folders. So `*.md` matches only the Markdown files at the root, and `**/*.md` matches them in every folder. Git's glob pathspec matches the same way. `git diff --name-only --no-renames <BASE_SHA>...HEAD -- ':(glob)<glob>' ':(glob,exclude)<glob without its !>'` prints the paths that make the gate apply. CI splits a rename into a delete and an add, so `--no-renames` lists both paths.

A gate that names gates in `after` runs only when each of them exited 0 earlier in the same gate run. Otherwise print `<NAME>_EXIT=BLOCKED` and the gate that did not pass. A `BLOCKED` gate is red. It is never a pass, and never a finding of its own.

Each gate runs in the CI environment of its jobs. Before its prerequisites, its `setup` commands and its command, the run exports `CI=true`, then each `ci_env` entry that has a `value`. An entry with a `why` and no `value` leaves its variable as the session has it, and that holds for `CI` too. The run never sets `GITHUB_ACTIONS` or another `GITHUB_` or `RUNNER_` variable, because no gate runs on GitHub Actions.

Each gate runs bun and the Supabase CLI at the versions in its `tools`, and so does each script that it starts. Before preflight step 8, get each version in the `tools` of each gate that applies. Make one new folder for the run with `mktemp -d`, outside the tree. For a `bun` version, link `bun` and `bunx` in `<folder>/bun-<version>` to the path that `bunx bun@<version> -e 'console.log(process.execPath)'` prints. For a `supabase` version, write an executable `<folder>/supabase-<version>/supabase` script with the lines `#!/bin/sh` and `exec bunx supabase@<version> "$@"`. Keep a folder only when its tool prints the version for `--version`. Otherwise delete the folder. In the subshell of each gate, put the folder of each of its tools first on `PATH`. Print `<NAME>_TOOLS=<tool>@<version>` for each tool, and add the local version for a tool that has no folder. When bunx cannot get a pinned version, the gate runs the local version. The final report names each difference as a note, and the run goes on. It is not an unclean stop. CI runs the pinned versions, and CI gates the merge. So a local run with a version note is advisory for that tool.

Print these rules at the start of every iteration, followed by the profile's `guardrails`:

- Gates decide. Reviewers only propose findings. Prose is not proof.
- Gates are read-only. No gate command, `setup` command or prerequisite runs `--write`, `--fix`, `--unsafe`, `--suppress`, `--update-snapshots`, `--apply`, a snapshot-update `-u`, `biome init`, `biome migrate` or `manypkg fix`. Such a command stops the run with principled incompletion. A gate that changes a tracked file outside its `rewrites` is red.
- No suppressions, no config weakening, no deleted or narrowed tests, no type laundering.
- With `typescript.rules` set to true, a fix proves or narrows a type. It adds no `as` assertion other than `as const`, and no `any`. It adds no `!` assertion, no angle-bracket cast and no double cast through `unknown`.
- Edit only the files a finding names. No dependency, lockfile, migration or CI edits, and nothing under `forbidden.paths`. A CI file is each path that `astack check ci-pins` prints with `the PR changes this CI file.`, also a script in the folder of a local action.
- The `managed` list in `.astack/profile.json` names the files that astack writes. Never edit one of them here. A finding on one of them is out of scope, and its fix goes to the astack repo.
- A fix can add a test or script that fails for the finding's reason. Run the failing check before the fix. Record its output. Then commit the test or script together with the fix, so every commit is green. The PR's Verification shows the failing run first, then the passing run. Each finding owns its commits. No commit holds two findings.
- Write each commit subject from `conventions.commit.subject`. End each commit with a trailer for each key in `conventions.commit.trailers`. Take its value from this session, such as the URL of the session.
- Push as `push` says. A push sends the branch of the fix commits, which the preflight names. A run with no PR, or with a PR from the same repository, pushes a branch with no upstream with `git push -u origin <branch>`. A branch that the preflight creates has no upstream. When `isCrossRepository` is true, the run pushes with `git push <head repository URL> HEAD:<headRefName>`, and never pushes a branch to `origin`. To make the head repository URL, start from the URL of `origin`. Replace its owner with the `login` of `headRepositoryOwner`, and its repository name with the `name` of `headRepository`. Never force-push, never push to the base branch, and never run a command that matches `forbidden.commands`.
- Print a value only when the profile holds it, such as a `ci_env` value. Never print a value from the session or from a file. Such a value can be a secret, such as a token, a key or a database URL.

Preflight:

1. Read the arguments, `$ARGUMENTS`. A bare word is the base branch. `--pr <number>` names the pull request. Without `--pr`, the PR is the one that the head check finds for the current branch, if any. With `--pr`, the base branch is the bare word, else the PR's `baseRefName`, whatever `base.from_pr` says. Without `--pr`, the base branch is the bare word, else the PR's base when `base.from_pr` is true and a PR exists, else `base.default`. Read the PR's base with `gh pr view <n> --json baseRefName`.
2. The working tree must be clean. If it is not, stop and ask what to do with the changes.
3. Run `git fetch origin <base>`. When it fails, or when `git rev-parse --verify origin/<base>` fails, stop with principled incompletion. The local base branch can be behind, so the run never diffs against it.
4. When `git diff --quiet origin/<base>...HEAD` exits 0, the branch has no change to review. Stop with principled incompletion, and create no branch.
5. Never commit on the base branch. If you are on it, create a branch named by `conventions.branch.create`. When `conventions.branch.pattern` is not null, the name must match it. Never create a review branch in a run with `--pr`. In a run with `--pr`, the fix commits go on the local branch of the PR. Without `--pr`, the fix commits go on the current branch, or on the branch that this step creates. In a run with a PR, read `gh pr view <n> --json headRefName,headRepositoryOwner,headRepository,isCrossRepository,maintainerCanModify`. When `isCrossRepository` is true and `maintainerCanModify` is false, the run makes no fix commit, and it stops with principled incompletion. The report says that the fork does not allow edits from maintainers, so the run cannot push a fix.
6. CI tests the merge of the branch into the base, so the gates need every commit of the base. When `git merge-base --is-ancestor origin/<base> HEAD` fails, the branch lacks base commits. With `base.sync` set to `merge`, run `git merge origin/<base>`. With `none`, print `git log --oneline HEAD..origin/<base>` and stop with principled incompletion.
7. Print `BASE_SHA` as the output of `git rev-parse origin/<base>`. Every diff of the run is `git diff <BASE_SHA>...HEAD`. When `command -v astack` succeeds, run `astack check ci-pins --base <BASE_SHA>`, and print its output and its exit code. It exits 3 when the diff changes only paths under `.github/workflows/` or `.github/actions/`, or in the folder of a local action that a workflow uses. For exit 3, each tool version that CI sets up stays the same, and the last line starts with `ci_proof:`. The check reads the tools of the setup steps, the runner, the container and service images and the ref of a remote reusable workflow. It does not read a tool that a `run` step or a script installs, so the review examines such a change. When the diff also changes another file, the check exits 1, because a red gate can then come from that file. A version file is a file that a workflow or an action names in a `-version-file` input. The check exits 1 when the diff changes a version file and the version that the setup action reads from it changes. It also exits 1 when it cannot read an exact version from a version file at `BASE_SHA` or at `HEAD`. It also exits 1 when the diff changes CI and a tool version that CI sets up, or when it cannot read such a version. When it exits 0 and its last line starts with `ok:`, the run goes on. When it exits 3 and its last line starts with `ci_proof:`, the run goes on in mode `ci_proof`. Otherwise stop with principled incompletion. With no node and no bun, the launcher prints a note and exits 0, so the exit code alone is not a pass. Another change to a version file, such as a new dependency in `package.json`, gets the gates of the run. When `command -v astack` fails, the run cannot do this check. Then stop with principled incompletion when the diff changes a path under `.github/workflows/` or `.github/actions/`, or a version file. Also stop when it changes a path in the folder of a local action that a workflow uses. The gates mirror the CI that astack apply read, and CI runs the workflows of the PR, so only CI can prove a CI change. In mode `ci_proof`, the run reviews, fixes and gates the PR as usual. It records the mode in the ledger, in each gate summary and in each PR comment. A red gate is advisory in that mode only with the proof below. The merge also needs the CI read-back of the steps after the stop. The mode follows the result of the last check of the run.
8. Install the dependencies in `WORKTREE` with a frozen lockfile, as the install step of CI does, such as `bun install --frozen-lockfile`. First delete the `node_modules` folder next to each `package.json` that git tracks, with `cd <WORKTREE> && git ls-files -z ':(glob)**/package.json' | while IFS= read -r -d '' file; do rm -rf -- "$(dirname -- "$file")/node_modules"; done`. A frozen install keeps a package that the lockfile no longer lists, and CI installs into a new checkout. Put the `bun` of the tools first on `PATH`. Do this in every run. A dev server or another session can use the `node_modules` folders of a checkout that the run did not create, such as the current checkout. So before the first delete in such a checkout, print `WORKTREE` and ask the owner. Without a yes, stop with principled incompletion. The yes holds for each later install of the run. When the install fails, stop with principled incompletion.
9. For each gate that applies, every `env` variable must be set. Put the tools of the gate first on `PATH`. Then run the `check` of each prerequisite in `requires` in the CI environment of the gate. Print its exit code. When a check fails and its `on_missing` is `start`, run its `start` command and check again. Run each `check` and each `start` with bash, in its own subshell from the root, as `( cd <WORKTREE> && <entry> )`. If a variable or a prerequisite is still missing, stop with principled incompletion before running anything. Name the gate and the missing item.
10. Load the ledger once per run, before the prepasses. Keep one ledger per branch at `$(git rev-parse --git-common-dir)/pr-review-hardening/<branch>.json`, with each `/` in the branch name replaced by `-`. The ledger holds `stopped`, the decision of the last run on the branch. It is `null` until that run stops. A ledger with no `stopped` key comes from a run that stopped. A ledger whose `stopped` is `null` comes from a run that was cut off, so this run resumes it, whatever `ledger.carry_over` says. A resumed run keeps each entry, and its first iteration is the one after the highest `iteration` of the entries. Otherwise, with `ledger.carry_over` set to `true`, start from the previous run's records. An entry that is `fixed` or `advisory` there is not raised again unless its file's blob has changed since. With `false`, rename an existing ledger to `<branch>.<UTC timestamp>.json` and start empty. Each run sets `stopped` to `null` at this load, and to its decision when it stops. Each run also sets `mode` to the mode of step 7 at this load, and to the mode of each later CI check. No iteration renames or empties the ledger, because `stop_recurring` reads the entries of earlier iterations.
11. Run each entry of `prepasses` whose `prepasses[].when` fits this PR, once, before the baseline. For `contract-coverage`, build a clause-to-control matrix over the specs that `prepasses[].sources` names. Plant a control for each clause that has no control. To check a control, remove the line of its clause. The control must fail. Then put the line back. Commit the controls and the matrix as findings `P.<k>`. Stop with principled incompletion on an entry with another name.

Gate run: run `git fetch origin <base>`, and do preflight steps 6 and 7 again. When the run has a PR, read its `headRefOid` again and do the head check again. A push to the PR can move its head. Run the install of the preflight again. Print `git status --short` as `GIT_STATUS_BEFORE_GATE`. When `git -C <WORKTREE> status --porcelain --untracked-files=all` prints a line, stop with principled incompletion before the first gate, and name each path. CI tests the commit, so a gate never runs on a file that the commit does not hold. Run every gate that applies, then the test gate. When `metrics` is not `null`, run `metrics.command`. Never re-create a metrics script from memory. Run each gate in its own bash subshell, such as `bash -c '<gate script>'`, as GitHub Actions runs a `run` step. Start the gate script with `set +e`. zsh does not split an unquoted `${name:+...}` into words, and it has no `PIPESTATUS`. Put its tools first on `PATH` and export its CI environment there. Print `<NAME>_TOOLS` and `<NAME>_ENV`. `<NAME>_ENV` lists the names that the run exports as `<name>=<value>`, which are `CI` and each `ci_env` entry that has a `value`. It lists each other name of the `ci_env` and `env` of the gate as `<name>=set` or `<name>=unset`. Run each `check`, `start`, `setup` command and the gate command in its own subshell from the root, as `( cd <WORKTREE> && <entry> )`. Before each gate, check its `env` and prerequisites again and run its `setup` commands in order. Also make sure that the script or binary of the gate command exists on this branch. If one fails, print `NOT_STARTED` for the gate with the reason, and stop with principled incompletion. Print each command as the profile writes it, with no variable expanded, and its exit code and output. Print a gate that does not apply as `SKIPPED`, with its globs. Before the subshell of a gate opens, record `git -C <WORKTREE> diff --name-only`. Right after it exits, whatever its exit code, the run restores the `rewrites` paths that were not in that list. It uses `git -C <WORKTREE> checkout -- <path>`. It prints `<NAME>_RESTORED=<path>` for each restored path that `git -C <WORKTREE> diff --name-only` showed before the restore. A `rewrites` path that changed before the gate stays as it is, so the status check after the gates shows it. Then print `git status --short` as `GIT_STATUS_AFTER_GATE`. If a tracked file changed after the restore, print its `git diff`. The gate is red, and the run stops with principled incompletion.

A red gate is a finding `G<n>.<k>` when the failure is in a file that the PR changed. It is also a finding when the same command is green on the base branch. Name the files in the failure output. Otherwise it is a pre-existing red. List it, and never fix it. The run cannot stop clean while it stays red. In mode `ci_proof`, a red gate is advisory when the run shows that the CI change of the PR makes it red. The proof names the changed line of the CI diff that the gate does not mirror. It also holds a run of the gate command as the CI of the PR runs it, and that run exits 0. The run gives the command what the changed line gives, such as an `env` value. When the PR removes a CI step that runs a gate command, the gates no longer mirror CI, so the profile must change. Then stop with principled incompletion, and name the step. Print the gate as `<NAME>_EXIT=<code> ADVISORY_CI_PROOF`, with the proof. Each other red gate blocks, as in the mode `standard`. CI on `PR_HEAD` still gates the merge.

Baseline: do the gate run once. Its metric values are the first budget. A `metrics` value of `null` means no metrics.

Each iteration:

1. Print `REVIEWED_HEAD` as the output of `git rev-parse HEAD`. It is the `<HEAD>` of the diff that the reviewers get. Launch the `pr-review-toolkit` review agents in parallel with the Agent tool. Tell each one to review `git -C <WORKTREE> diff <BASE_SHA>...<HEAD>`, with the path and both SHAs written out. Give each one every line of `reviewers.notes`. In mode `ci_proof`, also tell each one that the gates mirror the CI of the base. So only the review examines the CI files before CI runs. Also tell each one that `astack check ci-pins` does not read a tool that a `run` step or a script installs. A change to such an install is a blocking finding. With `reviewers.select` set to `all`, launch every agent in `reviewers.agents`. Otherwise launch `code-reviewer`, plus each agent in `reviewers.agents` that fits what the diff changes. Never run `/pr-review-toolkit:review-pr <base>`, which takes review aspects, not a branch. Never run `code-simplifier`, which edits code. Paste each output unmodified. Then examine the diff against each file in `reviewers.checklists`.
2. Triage each finding by its label. A finding is a blocking candidate when its reviewer label is Critical, Blocker, High or Important. A `normal` label is the same when the reviewer's machine output uses it to mean Important. A finding with an unclear label is a candidate until you triage it. Nit, Style, Suggestion, Pre-existing, Advisory and Informational do not block, unless the finding shows a gate failure. A checklist violation is a candidate too, whatever its label.
3. Reproduce each candidate. It blocks only when the reproduction shows a concrete failure that the PR introduces. That is a failing gate, a broken contract or documented rule, or added behaviour with no test. With `test_adequacy` set to `control-per-clause`, a planted control covers a contract clause when the control fails without the code of the clause. The coverage matrix of the PR names that control. Another input for a covered clause, such as another file extension, casing or character, is a suggestion. It is a correctness finding only when the code special-cases that input, and then it needs the input that triggers it. A missing test then blocks only when no control covers a clause. A defect with an input that triggers it, and a false sentence, also block. A bug fix with no cheap, correct test seam needs no test when its PR's Verification shows the failing run, then the passing run. It blocks again when the reproduction shows such a seam. Wording preferences, completeness wishes, true docs that can say more, refactors, style, nits and problems that the PR did not introduce never block. Mark a candidate advisory only for one of four reasons. Its reproduction fails on a second run, or it names code that is gone. It contradicts a green gate with no failing path, or it is pre-existing. Never mark a finding advisory because it is hard to fix. Record each finding with an id, file, reproduction, status, commits and blob in the ledger. The blob is the output of `git rev-parse HEAD:<file>` when the entry was last decided. When `git rev-parse HEAD:<file>` fails because `HEAD` holds no such file, such as a file that the branch deletes, the blob is `deleted`.
4. Fix each blocking finding for real, with its commits as the rules say. The gate findings of the last gate run are blocking findings too.
5. Comment gate. Invoke `astack:no-comments` over the diff if the Skill tool lists it. Otherwise delete every comment on an added or changed line unless it is on the keep list. The keep list is a license header, a note on behaviour that an external dependency forces, and `prettier-ignore` or a style-only suppression. It also holds a doc comment that defines a public API contract, and an issue or RFC link that explains a constraint. A comment stays too when it fits in 2 lines and one of its lines matches `comments.keep_patterns`, with or without its comment marker. A pattern that starts with a comment marker matches only a line with that marker. A pattern keeps only the lines that it matches. Delete the comment when another line, or the `rest` group of a pattern, holds a form that the hook denies. Those forms are provenance, narration, a `file:line` reference, the file's own path, a banner and commented-out code. Commit the deletions file by file.
6. Do the gate run. When `metrics` is not `null`, no key in `metrics.never_increase` may rise.
7. In a run with a PR, push the branch as `push` says when `HEAD` is not `PR_HEAD`. Then read the `headRefOid` of the PR again and do the head check again. Print a gate summary and a decision. If `proof.pr_comment` is set, post a comment on the PR. The comment starts with its heading, with `<n>` replaced by the iteration number. It holds the head SHA that the iteration ended on, the iteration number and the blocking finding count. It holds each gate command as the profile writes it, with its exit code, `SKIPPED`, `UNAVAILABLE`, `NOT_STARTED` or `BLOCKED`. It also holds the mode, and each advisory gate of mode `ci_proof` with its proof. Then it holds the decision and each item of its `extra` list.

Decide:

- `stop_clean`: the iteration found no blocking finding, the comment gate removed nothing and every gate exited 0 or is an advisory gate of mode `ci_proof`. Also, the metrics held, and at least `iterations.min` iterations have run. An iteration that commits a fix in step 4 is not clean, because no reviewer saw that commit. A clean stop also needs `REVIEWED_HEAD` to equal the output of `git rev-parse HEAD` after the last gate run. No reviewer saw a commit that comes after the review, such as the merge of a moved base in a gate run. A clean stop also needs a diff from the base that is not empty. In a run with a PR, a clean stop also needs `PR_HEAD` to equal `HEAD` after the push of step 7. CI tests only the head of the PR, so a review or a gate run of an unpushed commit proves nothing for the PR. In mode `ci_proof`, a clean stop also needs the mode in the gate summary, so the report names the mode. It also needs a CI read-back that passes on `PR_HEAD`, as the steps after the stop say, whatever `merge.after_clean_stop` says. A run of mode `ci_proof` without a PR stops with principled incompletion.
- `stop_recurring`: a finding came back after one fix attempt. Print the ledger and the suspected root cause. Do not try again.
- `stop_principled_incompletion`: a reviewer or gate cannot run, or a gate wrote a tracked file outside its `rewrites`. It also applies when a fix needs a file outside the fence, the git identity is missing, or the run reached `iterations.max`. It also applies in a run with a PR when `PR_HEAD` is still not `HEAD` after step 7, because the run cannot push. Then the report names each commit of `UNPUSHED`. It also applies when the PR is from a fork that does not allow edits from maintainers. It also applies in mode `ci_proof` when the CI read-back fails.
- Otherwise continue.

After the stop, when this run loaded the ledger, set its `stopped` to the decision. Then report the findings fixed, the commits and the metrics before and after. Also report each unresolved finding with its reason, and the final gate output. Name each commit of the last `UNPUSHED` list, because CI did not test it. Name each tool that a gate ran at its local version as a note. CI runs the pinned versions, and CI gates the merge. So a local run with a version note is advisory for that tool. Also report the mode of the run, and in mode `ci_proof` each advisory gate with its proof. On an unclean stop, do what `proof.on_unclean` says when it is not `null`. With `draft` set to true, return the PR to draft with `gh pr ready <n> --undo`. When `label` is set, add that label to the PR. Create the label first with `gh label create` when it is missing. Post each unresolved finding with its exact reason to each place in `post_to`. The place `issue` is the issue that the first line of the PR body names. If `threads.answer` is true, answer each review-bot thread on the PR before the merge. Fix each thread, or refute it with the reproduction. Then resolve it. Never resolve a thread without a fix or a reply. Merge only when `merge.after_clean_stop` is `merge` and every line of `merge.conditions` holds. In mode `ci_proof`, merge only when the CI read-back passes. For the read-back, read `gh pr view <n> --json headRefOid`, then `gh pr checks <n> --required --json name,state,bucket,event,workflow,link`, then `headRefOid` again. Both reads of `headRefOid` give `PR_HEAD`. The list holds at least one required check, and each one has the `bucket` `pass` and the `event` `pull_request`. A `pull_request` run takes its workflows from the merge of the PR head into the base, so it ran the CI of the PR. When a required check is still `pending`, wait with `gh pr checks <n> --required --watch`. Then read again. Then use the merge command of the profile. Otherwise never merge.
