# Working on astack

`docs/design.md` is the authoritative design. Read it before you change the layout or a hook.

## Where things live

- `marketplace/` is the client-neutral Claude Code marketplace `astack`, publishable on its own. It holds the `astack` plugin.
- `marketplace/plugins/astack/` holds the source files of the plugin: skills, agents, `hooks/hooks.json`, the `bin/astack` launcher and the bundled CLI `bin/astack.js`. `scripts/lib/residuals/` holds the residual allow lists.
- `src/astack/` holds the astack CLI sources. `src/astack/hook/` holds the hook dispatcher, and `src/astack/cli/` holds the command registry.
- `.astack/profile.json` in a product repo is the astack profile of that repo. `src/astack/profile.ts` reads it.
- `rules/` holds the always-on rules that users symlink into `~/.claude/rules/`. `rules/astack.md` is the rule card. It is a copy of the mode's `references/card.md`, so the plugin carries it too, and a project apply never copies it into a repo.
- `src/astack/rules.ts` owns shared rule names and selection for installs, migration, doctor, and builds. The scoped packs are `rules/typescript.md` and `rules/postgres.md`.
- `src/astack/hook-profile.ts` parses `hooks.profile` and its `ste`, `types`, and `comments` overrides. Strict is the default. Minimal disables only those quality groups. Every unmarked handler stays required. Invalid settings retain strict runtime behavior. CLI checks stay independent. See `docs/runbooks/hook-profiles.md`.
- `upstream/` holds pristine snapshots of the pinned upstream plugins. `upstream/lock.json` records the repo, path and commit of each.
- The companion is a private folder of the owner, outside this repo. It holds the apply configs, their hardening profiles and the deny list. `scripts/lib/companion.ts` owns its layout. Apply, `bun run deny`, `bun run neutral` and `bun run check:companion` find it through `--companion <dir>`, then `ASTACK_COMPANION_DIR`, then the synthetic `examples/companion/`. The tests always use the example, and a write refuses it. `bun run check:companion` examines each config and profile of the companion, and fails on 0 configs. It also runs each test file that reads `profilePaths` or `scanProjectDirs` from `tests/profile-paths.ts`, with `ASTACK_PROFILE_SCAN_DIR` set to the companion. So the profile and config scans of the tests read each profile and overlay of the companion, with the exception rows of its `profile-scan.json`. It runs each `tests/*.test.ts` of the companion too.
- `projects/<name>.json` in the companion holds the apply config for one project. Its `tracker`, `merge`, `ste`, `domain` and `keepPatterns` fields become the repo's `.astack/profile.json`. Its `commentConflicts` list the open comment-rule conflicts, and its `commentDecisions` record the owner's decisions. `projects/<name>/pr-review-hardening.profile.md` is the hardening profile of that repo. The `branches` object of `projects/<name>.json` holds an overlay for each base branch with its own CI, such as `v2`. An overlay sets only `gates`, `ciOnlyGates` and `ciParity`, and each other key comes from the top of the config. `projects/<name>/branches/<branch>/pr-review-hardening.profile.md` is the hardening profile of the overlay. `scripts/lib/projects.ts` fails a config when that file is missing. An apply whose `--base` names that branch uses the overlay for the CI parity check and writes the profile of the overlay. An update takes the overlay from `--overlay <branch>`, and the README gives the rule that refuses an update without it. A decision citation is a comment that cites an ADR, such as `ADR-0006`, or a comment line that starts with `Source:`. Apply sends each citation of the repo through the comment hook with `keepPatterns`, and fails on a citation that the hook does not keep.
- `templates/pr-review-hardening.stub.SKILL.md` is the one review stub that apply writes into each repo. Its fallback has no defaults, so each profile defines every key in `FALLBACK_KEYS` in `src/astack/pr-review-profile.ts`. The fallback does not follow the keys in `FALLBACK_UNREAD`, so apply refuses a stub profile that sets one of them away from its default.
- The gates of a hardening profile mirror the blocking jobs of the repo's CI. `scripts/lib/ci-parity.ts` reads each pull request workflow of the repo and maps each job to a gate by its commands. The `ciParity` field of `projects/<name>.json` holds the rest. `setup` lists the CI commands that check nothing. `map` maps a job, or one of its steps, to gates. `exclude` lists the advisory and nightly jobs and steps. An exclusion of a job needs proof in the workflow. The proof is `continue-on-error`, an `if` that is false on a pull request without a label, no command, or an aggregate of mapped jobs. `narrow` lets a gate run on fewer paths than its job. Each entry gives its reason. Apply prints the map. It fails on a job with no gate or a gate that skips a path of its job. It also fails on an exclusion with no proof and on a stale entry. The check also reads the `env` of the workflow, of each mapped job, of its `container` and of each mapped step. It compares them with the `ci_env` and `env` of the gate. In a job that the config maps as a whole, each step that does more than prepare a gate is a mapped step. It fails on a variable that the gate does not set or leave out with a `why`. It also fails on a copied value that differs from CI and on a stale copy. The run exports `CI=true` for every gate, as GitHub Actions does, and never fakes `GITHUB_ACTIONS`. The check reads the tool versions that `oven-sh/setup-bun`, `supabase/setup-cli` and `actions/setup-node` pin in each mapped job. A gate records the bun and Supabase CLI pins in its `tools`, and the run gets those versions through bunx. The check fails on a gate that does not record a pin of its job, or records another version. It also fails on a gate that records a tool that no job of the gate pins. A tool that only a prerequisite or a setup entry of the gate runs is the exception. Its version must be a pin of another job of the profile. A gate records each pinned tool that it runs, because the run puts only the tools of the gate on the PATH. A node pin needs a prerequisite that checks the version. `src/astack/ci-pins.ts` holds the three setup actions and the reader of the version in a version file. The bundle of the CLI builds from `src/astack/` only, so the reader is there, and the parity check imports it. `astack check ci-pins` uses the same reader in preflight step 8 of the hardening run. It stops a run when the PR changes a version that a setup action reads from a file. When the PR changes only CI files, it compares the tool versions of CI at the merge base and at HEAD. A tool version is the version that setup-bun, setup-cli or setup-node gets. It is also the value of a `version` or `toolchain` input of another action. Such an input name can have a prefix and a `-file` suffix, each with `-` or `_`. The pin of such a step also holds its `uses` value with the ref, each other input and its `if`. Each of them can change the tool that CI gets. Each job also holds its runner, its container and service images and the ref of a remote reusable workflow that it calls. A remote action whose name looks like a setup action holds its ref, also with no version input. The check does not read a tool that a `run` step or a script installs, so the reviewers examine such a change. The tool versions of a local action or a local reusable workflow count in the job that calls it. They count in step order, with the inputs of that call only. Each job that both sides hold must set up the same versions in the same order. A job that loses its last setup step changes. A new job can set up only a version of the merge base. When the PR also removes a job that sets up a tool, a new job with a tool is a change. A rename can move a version from one job to another. Then the check exits 3, its last line starts with `ci_proof:`, and the run goes on in mode `ci_proof`. A tool version change, a form that it cannot read on either side and an expression in a version input exit 1. A PR that also changes a file outside CI exits 1, because a red gate can then come from that file. In mode `ci_proof`, a red gate is advisory only with a proof that the CI change of the PR makes it red. A clean stop and the merge need each required check of the PR head to pass on a `pull_request` run. That run takes the workflows of the PR. The reader reads a file as the setup action reads it, in the same order and with the same truthiness. A setup-bun step whose `bun-version` can be empty falls back to `package.json`. When the `version` of `supabase/setup-cli` can be empty, the action reads the root `bun.lock`, then `pnpm-lock.yaml`, then `package-lock.json`. The check reads them in the same order. The bundle also runs on node, which has no YAML parser, so the CLI bundles the `yaml` package. GitHub's own workflow parser for TypeScript uses that package too. The check reads each file with it as YAML 1.2. It stops the run on each YAML form that YAML parsers can read in different ways. Such forms are a parse error or warning, a tag, an alias, a merge key and a key that the map repeats in any case. An anchor name with a character that is not a letter, a digit, `_` or `-` stops it too. So do a tab in an indent, a directive and a second document. A lone CR, a line break that only YAML 1.1 reads and a byte order mark after the start also stop it. A key that holds `${{` stops it too, because GitHub evaluates such a key. The check reads the root keys `inputs` and `runs` of an action only in lower case, as the runner does. Another case of them stops the run. A `${{ inputs.<name> }}` value of a local action resolves to the value of each caller, or to the default of the input. In a workflow it can also be empty, because a pull_request run gives no inputs. A null or blank input is empty, as `getInput` gives it to the action. The check names a remote action as the runner splits its `uses` value. It maps a renamed repo to the repo that GitHub redirects to. A `uses` value that starts with `./`, `.\\` or `$/` is a local action. setup-bun picks its reader by the basename of the input as written, and the check does the same. When `<ref>` moves after the merge base, the check also compares the merge base with `<ref>`, because a pull_request run tests the merge. A version file that is missing or is not a regular file also stops the run. So does a local action that the repo does not hold. A gate names in `rewrites` each tracked file that a tool of the gate writes, and the run restores those files after the gate. `scripts/lib/next-env.ts` finds each gate that runs `next build` or `next dev` in an app with a tracked `next-env.d.ts`. It also finds a write through an output redirect, `tee` or an `-o` or `--output` flag. Apply fails when that gate has no `rewrites` entry for the file, and when git does not track a `rewrites` path. `scripts/lib/env-files.ts` finds each gate that runs a script or a runtime in an app folder with a tracked env example, such as `.env.example`. It follows the scripts of the repo to each app that a web server of a Playwright suite starts. Apply fails when git ignores the env file of that example and no prerequisite of the gate names an ignored env file of that folder. `scripts/lib/task-cache.ts` follows the `bun run` scripts of each gate through the `package.json` files of the repo, also in the short form `bun <script>`. Apply fails on a gate whose scripts run a fixer flag, such as `--write`. Apply fails on a gate that runs a turbo task with no `--force` when the gate does not set `TURBO_FORCE` to `true` in `ci_env`. A task with `cache: false` in `turbo.json` needs neither. `scripts/lib/platform-tools.ts` follows the same scripts, and each file that a script runs, to a tool that only one platform ships, such as `lockf`. Apply fails on a gate that reaches such a tool, unless a prerequisite check fails when the tool is missing, such as `command -v lockf`. A check that ends in `|| true`, `|| echo` or `; true` passes on each host, so it does not count. An if in the gate command can guard the tool too. Its condition must fail when the tool is missing, and its else branch must run a portable form without the tool. The rest of the command, outside each such if, must not reach the tool. A gate that applies migrations to a local stack that lives longer than one run runs `astack check migrations` before and after `supabase migration up`. `src/astack/migrations.ts` compares the statements that the stack recorded with the migration files. A gate on such a stack starts it with `astack stack start`, and has a prerequisite that runs `astack check stack-config`. The parity check compares the `--run` command of that start with the start step of CI. It ignores a redirect of standard output to `/dev/null`. `src/astack/stack-config.ts` compares a digest of the watched files of the checkout with the record that `astack stack start` wrote when it started the stack.
- `src/astack/managed.ts` lists the files that apply deletes and merges. Apply writes the `managed` list of each repo into its `.astack/profile.json`, and `astack managed <path>` reads it. A review finding on a managed file gets its fix here, and then an apply with `--update` to each repo with a profile. Apply fails on a tracked copy of the review stub or of the hardening command at a path that it does not write or delete. `scripts/lib/line-citations.ts` fails apply on a tracked Markdown file outside the managed list that cites a managed file with a line number, such as `.claude/pr-review-hardening.profile.md:12`. Each apply update can move that line. The subject of each apply commit names the files that the commit deletes. An apply with `--worktree` refuses an astack tree with no commit, or with an uncommitted change in `marketplace/`, `rules/`, `scripts/`, `src/`, `templates/` or `upstream/`. It also refuses a companion with no commit or with an uncommitted change. Its commit names the astack commit in an `Astack-Commit` trailer, and the companion commit in a `Companion-Commit` trailer. With `neutralCommit` in the project config, the subject and the body name no tool, and the trailer key is its `provenanceKey`. Apply refuses such a commit message when it holds a substring of `lint.denySubstrings`. Apply also writes that list into `neutral.deny` of the repo's `.astack/profile.json`. A check in the repo then reads the same list.
- Each repo-bound file that holds upstream text declares its source in `scripts/lib/render.ts`. Apply then adds a pointer to `.astack/NOTICE`, which holds the MIT notices. `tests/apply/notices.test.ts` fails when a rendered file shares a run of words with an upstream file that it does not declare.
- `scripts/` holds the build, apply, validate, dist and neutrality scripts. `scripts/dist/` holds the per-tool renderers and their checks.
- `dist/` holds the generated install builds, with one folder per tool. The public source root points to them through generated marketplace manifests.
- `tests/` holds unit tests and synthetic fixtures. `tests/fixtures/hook-input/` holds synthetic hook payloads with the shapes that Claude Code sends.
- `docs/` holds the design. `docs/migration.md` is the switch from the old agent-stack install, and `bun run apply --global --dry-run` prints the same steps. `docs/review-lessons.md` records each class of review finding with its rule and its guards. `tests/review-lessons.test.ts` compares it with the guard files and with the review checklist of the engine, `references/checklist.md`.

## Add a hook handler or a CLI command

`hooks/hooks.json` has one dispatcher entry for each event and stays the same byte for byte. Do not edit it to add a check.

1. To add a hook check, write `src/astack/hook/handlers/<id>.ts`. Make the handler with `defineHandler({ id, on, run })` from `src/astack/hook/events.ts`, and export it as `handler`. `on` lists the event kinds. `run` gets only those kinds and returns a `Verdict`.
2. Add the handler to the array in `src/astack/hook/handlers/index.ts`.
3. To add a command, write `src/astack/cli/commands/<name>.ts`. Export `command` with `name`, `summary`, `usage` and `run`, and add it to `src/astack/cli/commands/index.ts`. A new check goes in `src/astack/cli/commands/check/` and in `check/index.ts`. Then `astack check <name>` and `astack check-<name>` both run it.
4. Read a repo setting with `profileSection(projectDir, "<key>")` from `src/astack/profile.ts`, and parse it in your own module.
5. Return a verdict. Never write to stdout or stderr in a handler. `src/astack/hook/encode/` turns the combined verdict into the output of each tool.

## Never hand-edit generated files

Change the source and rerun the command.

| Generated file | Source | Command |
|---|---|---|
| `rules/astack.md` | `marketplace/plugins/astack/skills/mode/references/card.md` | `bun run build` |
| `docs/migration.md` | `scripts/lib/migration.ts` | `bun run build` |
| `marketplace/plugins/astack/NOTICE` | the origins of the astack items and `scripts/lib/upstreams.ts` | `bun run build` |
| `marketplace/plugins/astack/bin/astack.js` | `src/astack/` | `bun run bundle` |
| `dist/` | `marketplace/`, `rules/` and `scripts/dist/` | `bun run dist` |
| `.claude-plugin/marketplace.json`, `.cursor-plugin/marketplace.json` | `scripts/build.ts` and the source marketplace | `bun run build` |
| `LICENSE`, `NOTICE` | the astack plugin licence and notice | `bun run build` |
| `package.json` name, version, private, author, license, bin and engines | the astack plugin manifest and `scripts/build.ts` | `bun run build` |

Never edit `upstream/`. It holds frozen snapshots, and no script syncs or ports them (ADR 0001). To take a useful upstream change, copy it by hand as a normal astack change.

`rules/comments.md` is a source file, but never change its four quoted sections or its copyright line. `tests/build.test.ts` compares them with the frozen pstack agent and licence.

## Keep the tree client-neutral

No tracked file names a client, a client project, or a customer. No tracked file holds a value of another leak class of `scripts/lib/leak-rules.ts`, such as a local path or a session id. Put project-specific material in the companion, and use synthetic fixtures in tests. `bun run neutral` reads each tracked file and exits 1 on a finding. With the owner's companion, it also reads the owner values of the companion.

## Build the dist

`bun run dist` writes `dist/` from `marketplace/` and `rules/`. Then it runs the checks of each target. The public repo holds the source and these client-neutral builds. The root marketplace manifests point to `dist/`.

| Folder | Tool | What it holds |
|---|---|---|
| `.claude-plugin/`, `claude-code/` | Claude Code, Codex, Grok Build | the marketplace `astack` with a copy of the `astack` plugin, plus `agents/openai.yaml` beside each skill that only the user may start |
| `rules/` | Claude Code, Grok Build | the rule card, coding and comment rules, and scoped language packs, which the owner links into `~/.claude/rules` |
| `.cursor-plugin/`, `cursor/astack/` | Cursor | one plugin with each kept skill and agent as `astack-<name>`, `rules/*.mdc` and Cursor hooks |
| `codex/` | Codex | install steps, `AGENTS.fragment.md`, the hash of `hooks.json` and `hooks.trust.json` with the hash of each hook |
| `grok-bot/` | Grok Bot | flat skills, `astack-rules` and `astack-sync`, and no hooks |
| `agentskills/` | other Agent Skills clients | skills with only `name`, `description`, `license` and `metadata`, and `AGENTS.fragment.md` |
| `package.json`, `cli/astack.js` | CI and git hooks | the CLI package |

- `scripts/dist/capability.ts` decides for each item and tool whether the build emits it, omits it or uses a fallback. Add a case there before you add a target or an item.
- Codex trusts a hook by its hash. `scripts/dist/checks.ts` pins the sha256 of `marketplace/plugins/astack/hooks/hooks.json`, so the build fails when the file changes. Change the file only on purpose. Then change the pin. `src/astack/codex-trust.ts` pins the hash that Codex shows for each of the four hooks. When `codex` is on PATH, `bun run dist` reads them from `codex app-server` in a temporary `CODEX_HOME` and fails on a mismatch. `astack doctor` compares the trusted hashes of the owner with these pins.
- A skill that holds upstream text names each upstream in `metadata.origin` of its frontmatter, such as `origin: pstack mattpocock-skills`. Claude Code warns on `metadata` in an agent, so `AGENT_ORIGINS` in `scripts/lib/upstreams.ts` holds the origin of each agent. `PATH_ORIGINS` holds the origin of each code and rule file. The licence of each flat skill holds the copyright of each origin upstream, and `bun run build` writes `marketplace/plugins/astack/NOTICE` from the origins. `tests/notice.test.ts` fails when an item shares a run of 8 words with an upstream that its origin does not name. `tests/dist/real.test.ts` fails when a flat skill shares a run of words with an upstream that its licence does not name.
- The flat targets must not hold terms of Claude Code. `scripts/dist/claude-terms.allow` lists each allowed term with its reason, in the format of the residual allow lists.
- `upstream/cursor-plugin-schemas/` holds the pinned Cursor manifest schemas. The build compares the Cursor manifests with them.
- The copy of the astack `plugin.json` in `claude-code/` gets a build stamp, such as `0.1.0+1a2b3c4d5e6f`. The stamp is a hash of the plugin files, so `claude plugin update` sees each new bundle. The release version in `marketplace/` and in `package.json` has no stamp.

## Write no comments

pstack's `upstream/pstack/agents/comment-sicko.md` is the ruler for code in this repo. Names, types and tests carry intent. A comment survives only if it is one of these:

- a license or SPDX header;
- a note on non-obvious behavior that an external dependency, platform, vendor or protocol forces;
- a `prettier-ignore`, or a style-only lint suppression with its reason;
- a doc comment that defines a public API contract;
- an issue or RFC link that explains a constraint the code cannot express.

## Write plain prose

Skills, rules and docs follow the `astack:write-docs` and `technical-writing` skills. Write short sentences with no filler, no emoji and no bold labels.

astack's own text must also pass the ASD-STE100 deny rules with zero findings. That is the Markdown under `marketplace/plugins/astack/`, `rules/`, `docs/`, `templates/` and `examples/`, `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, `SECURITY.md` and each skill description. `bun run validate` runs that gate, and `scripts/lib/ste-own.ts` lists the files and the exemptions. The gate also examines the Markdown that apply renders for each project of `examples/companion/`, so a sentence in `scripts/lib/flow-config.ts` must pass too. `bun run check:companion` examines the profiles of the companion and the Markdown that apply renders for each of its projects. The exemption cap is 0. Do not add prose exemptions. The gate skips the four protected upstream quotations in `rules/comments.md`. Fix a finding at its source, never in a generated file. To see the findings of one file, run `bun src/astack/cli/bin.ts check-ste <file>`. `bun run ste` runs the precision gate on `tests/fixtures/ste/labelled.txt`. The STE engine is in `src/astack/ste/`, and `docs/ste-targets.md` maps the reply rewrite to Cursor and Codex.

## Test plugins in isolation

Load a plugin with `claude -p --plugin-dir <dir> --no-session-persistence` from a temporary directory. Set `CLAUDE_CONFIG_DIR` to a temporary directory too, because `claude -p` still writes `projects/<slug>/` into the config dir. A temporary config dir has no login, so export `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` first. `bun run validate` does this for its load gate when one of them is set. When neither is set, it prints SKIP for the load gate and never runs it against your own config. Never install a work-in-progress plugin into your real Claude Code config.

## Check before you commit

Run `bun run check:drift` before a rebuild. It compares fresh expected artifacts without changing generated files.

Run `bun run check`. It builds, bundles, validates, builds and checks `dist/`, runs the neutrality lint, the STE gates and the tests, and then runs `biome ci .` and `tsc -p .`. It also runs the secrets scan of `bun run secrets`. The secrets scan puts the pinned gitleaks into the astack cache folder, so its first run needs network access. To fix formatting, run `bunx biome check --write .`.

The owner's clone also runs the scan as its git pre-push hook, with `bun scripts/pre-push.ts --companion <companion> "$@"` in `.git/hooks/pre-push`. The flag names the companion also when git runs the hook without the shell profile. The hook acts only on a push to the `publicRemote` of `machine.json` in the companion. It then scans each file of each new commit. It exits 1 on a finding or on an empty deny list. It also refuses the example companion, because the example holds no owner value.
