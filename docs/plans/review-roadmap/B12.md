## Domain and effects

```domain
context Delivery
agg  ReviewRecord @ src/astack/review-record.ts: ReviewRecord
inv  RR1 ReviewRecord: baseSha and firstReviewedHead never change, and each new head joins the end of heads
inv  RR2 ReviewRecord: a delta run starts only from the last stop_clean head that HEAD holds
step loadRecord : string -> Eff<ReviewStore.loadRecord, RecordProblem, ReviewRecord>
step withHead : (ReviewRecord, ReviewedHead) -> ReviewRecord
step deltaBase : (ReviewRecord, string[]) -> DeltaBase
step saveRecord : (ReviewRecord, string) -> Eff<ReviewStore.saveRecord, StoreProblem, void>
law  L1 RR1 withHead keeps both first-review fields and puts the new head last   check: prop review-record-append
law  L2 RR2 deltaBase gives the last stop_clean head of the ancestor list, else full   check: prop review-delta-base
law  L3 ReviewStore a saveRecord and then a loadRecord of one path give an equal record   check: prop review-store-roundtrip
rung R4
```

- L1 and L2 tag an inv and L3 a write cap, so each gives R3. The Files rung is R4, because CiProofRecords covers both ci-pins files.
- `deltaBase` takes the recorded heads that HEAD holds, which the command reads with git. So it stays pure.
- `DeltaBase` is `delta` with a sha or `full` with a reason. `RecordProblem` is `missing` or `unreadable`.
- `ciMode : CiFacts -> CiMode` is pure. The ci-pins command keeps its effects, and no new composite arrow needs a category law.

The record steps.

- The record stays beside the ledger, at `<git common dir>/pr-review-hardening/<branch>.review.json`. A head holds `sha`, `decision` and `launches`.
- `saveRecord` writes a temporary file and renames it, as pr/grant-store.ts:49-51 does. The atomic control fails a save and reads the old record.
- `astack review base --head <ref>` prints both first-review fields, the launch total of the PR and a last line.
- That last line is `delta: <sha>` with exit 0, or `full: <reason>` with exit 3. A git or read failure exits 1, and wrong arguments exit 2.
- It runs git with `--no-replace-objects`, as change-proof/candidate.ts:202 does, so a replace ref cannot fake an ancestor.
- `astack review record --base <ref> --head <ref>` creates an absent record. With `--decision` and `--launches`, it adds a head.

## Risks

- An agent can write a false clean head into the record. The record is a mistake guard, and the gates and the merge grant still apply.
- A delta after a merge of the base also reviews the base changes. That costs launches only.
- A pinned older CLI prints no rung line, so that repo keeps the applicable set.
- B30 step 3 edits docs/review-lessons.md and the Apply area of checklist.md. The later PR merges main, and its move keeps the B30 item.
- B30 can land before step 11. Then the ADR follows its template and passes `astack check adr`.
