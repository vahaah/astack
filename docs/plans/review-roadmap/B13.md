## How each step runs

- Each code step starts with a test that fails for the reported reason. The fix lands in the same commit.
- The name of each test that guards a criterion holds `[control:<id>]` with the criterion id in lower case. The matrix refuses a control id in two files, so a second test of one criterion adds a suffix, such as `cwd-free-plan`.
- Step 7 declares the criteria in `docs/reference/plan-boundary.md`, because the matrix reads criteria from a spec file. `tests/tracker-schema.test.ts` holds the control of the step 5 greps.
- Each text edit pays for its new words in the same skill, because the budget gate is at its cap. Step 7 lowers each cap to its new count.
- The typed composition for the proof is `readAdr` (fs-read) then the pure `decisionHeading`. The plan commands run `planStateFor` (fs-read, git), then the pure `parseTrailBatch`, then one `appendTrail` (fs-write). A batch with a bad row writes nothing.
- Step 7 writes the proof manifest last, because its scope lists each path that the session changes. When another PR merges first, merge main into this branch and run step 7 again.
- Step 7 takes the ADR number that the index reserves for B13. Today that is 0020, because B03 took 0021 and B09 took 0022. When the index gives another number, change D8 and step 7 first.
- Step 1 moves `adrProse` into `src/astack/adr.ts`, so `proofSections` and the reader mask fences in one way.
- In step 2, an argument that ends in `.md` is a plan path, and each other argument is a slug. An empty batch is a usage error. `template.md#trail` gives one example batch row.
- Step 4 starts only after B09/S1 merges, because B09 edits `mask.ts` and `ste.test.ts` too. Merge main into this branch first. Steps 1 to 3 do not wait.
- Before the fix, step 4 records one run that fails on each line of the span fixture.
- Step 5 tells the integrator to add the plan file to the proof scope of the session that carries the boundary edit.
