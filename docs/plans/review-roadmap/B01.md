# The merge guard takes authority only from a person's prompt and the base branch profile

This block closes the merge authority leaks that the review found in code.
It gives the first part of the M1 demo.
A harness brief, a working-tree profile edit and a host MCP merge tool each fail to merge.

## Context

- Review `C1a`. `humanPrompt` in `src/astack/ste/session.ts` refuses only a prompt that opens with a `<tag>`. A workflow brief opens with `[Workflow harness`. So its "Merge #12 when green." text saves a merge grant.
- The Cursor decoder in `src/astack/hook/decode/cursor.ts` marks each prompt as human. It ignores the attended state that its session start reads.
- Review `C3`. `mergeVerdict` reads `.astack/profile.json` from the working tree through `loadPrProfile`. An uncommitted edit gives standing merge authority, also in an unattended session.
- Review `C2`. `mcpVerdict` denies only two tools of a server whose name holds `github`. The CoCode `pull_request_merge` tool and the Linear `merge_diff` tool merge with no deny.
- `grantReasons` returns at once for `merge.authority` set to `standing`, before the repo check. So that profile also allows a `--repo` merge of another repo. A standing base of another repo still needs a grant, as `tests/astack/merge-guard.test.ts:450` shows.
- `judge` in `src/astack/hook/dispatch.ts` turns a handler exception into an allow. So an error in the merge guard lets the merge go ahead.
- A GraphQL `Commit.file` read of an absent path exits 1, and `ghJson` drops the reply. A `repository.object(expression:)` read returns null and exits 0. The spec review probed both.
- The SessionGuards model has no prompt text, no working-tree state and no tool kind. So `MergeNeedsAuthority` holds on each leak trace.
- The design sketch is on the local branch `sketch/review-roadmap`. Its rationale is `docs/plans/review-roadmap/sketch-rationale.md` on that branch.

## Goal

Goal. A merge goes ahead only with a grant that the owner typed in this turn, or with the profile on the PR base branch.
Decision. Can the owner give an agent standing merge authority and trust that nothing else widens it?
Done when. The three review probes each get a deny. Today 0 of 3 get a deny.

## Scope

- In. A probe of the prompt payloads of the host relay channels and of the host MCP tool schemas, with fixtures.
- In. A frame rule for harness text in the Claude Code and Cursor decoders, and the attended check in the Cursor decoder.
- In. Standing authority from `.astack/profile.json` at the tip of the PR base branch, through the PR read, for the PRs of that repo only.
- In. A deny for each MCP tool whose name holds a `merge` token, on each server.
- In. A deny when the merge guard throws on a merge event.
- In. Each caller and control of the old profile read, with ADR 0011, the SessionGuards model and the proof manifest.
- Out. The shell wrapper bypasses of `--admin` and the `gh api` REST merge form. B04 owns them.
- Out. The host request for `source` set to `user`. The owner files it, and B04 owns the astack side.
- Out. A hostile agent that writes the grant file or calls the REST API with its own tool. Question 3 decides that threat model.
